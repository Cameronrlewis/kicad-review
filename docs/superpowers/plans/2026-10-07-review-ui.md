# Review UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the current single-template report (`report.html`) with a review screen whose layout and flow follow KiHub's review workspace: a header, a file and sheet navigator with change counts, a drawing area with five comparison modes, a board layer list, a change list with two-way selection, a checks view, keyboard stepping, addresses that record the view, and light and dark themes.

**Architecture:** The page lives in `ui/` as three files: `review.html`, `review.css` and `review.js`, in plain HTML, CSS and JavaScript. In development the page loads `ui/sample/review-data.js`, real data from the test project. In CI, `kicad_review.py report` inlines the CSS, the JS and the run's data into one self-contained `kicad-review.html`. Data format v1 is the only contract between the workflow and the page. Drawings are KiCad SVGs inserted inline and moved with a CSS transform, using `will-change: transform` while panning and zooming. Objects are located by coordinates, because the renders carry no identifiers.

**Tech Stack:** Python 3.11+ standard library (workflow side). Plain HTML, CSS and ES2022 JavaScript with no build step (page). Node 22 and the local Chrome for the headless check harness (development only, no npm packages). The `ui-ux-pro-max` plugin's `design` / `design-system` / `ui-ux-pro-max` skills for tokens and UX rules.

**Spec:** the brief "design and build the user interface for my KiCad review tool" (conversation of 2026-10-07), plus Part A below (the observations and decisions made against it). Executors read both.

## Global Constraints

- No server and no database. Everything the page needs is inside the one HTML file, and nothing is fetched at view time: no web fonts, no CDN, no `fetch()`.
- The page must work when opened from disk (`file://`).
- Plain HTML, CSS and JavaScript. No framework, no npm dependency in the shipped page, no build step beyond the inlining `kicad_review.py` already does.
- Do not copy KiHub's name, logo, wording, icons or image assets. Reproduce how it works, not who made it.
- Design for wide desktop monitors (≥ 1920 px) first. Must stay usable at 1366×768. No phone layout.
- Added, removed and modified must be distinguishable without colour: each has its own glyph, outline style and text label.
- Light and dark themes follow `prefers-color-scheme`. There is no in-page theme store.
- Leave out: server or database, sign-in, stored comment threads, approval buttons, full commit-history browsing, design editing, anything in the ParadigmEngineering organisation.
- Do not build any of the access options in Part A §6 until the user chooses.
- Show the user a screenshot after each build stage (Tasks 3–10) and say what could not be verified.

## Review Focus

1. **A project with only one side.** It may be added (no base), removed (no head), schematic-only or board-only. The navigator still lists it with correct counts, the drawing shows the one side, and no mode throws. Test in Task 3 and Task 5.
2. **A reused hierarchical sheet**, where the same `.kicad_sch` appears twice under different sheet UUIDs. It gives two navigator entries with separate counts, and selection lands on the right instance. Test in Task 3 and Task 7.
3. **A dense board** (KiCad `vme-wren` demo, about 74k SVG elements across two copies). Panning keeps a p95 frame time ≤ 20 ms in headless Chrome, and first paint is ≤ 5 s. Test in Task 4.
4. **An address from a different report** (an unknown project index, sheet path or selection id, or a malformed number). The page falls back to the first changed item at fit zoom and never shows a blank screen. Test in Task 9.
5. **A violation without a position**, such as a parity item with `items: []`, or a violation on a sheet that did not change and has no render. It is listed with "no location", clicking it does not move the drawing, and no error is thrown. Test in Task 8.

### A1. What KiHub's review workspace does (observed 2026-10-07)

**How I looked.** I used headless Chrome driven over the DevTools protocol, because the Chrome extension was not connected. I went through the public demo library at `app.kihub.dev/demos` and opened three of its six reviews. One was the `nest-mini` board and schematic compare, which has 345 changes. One was the `OSLUV` five-file compare, which has several schematics. I also listed the files in the remaining demos. I declined analytics in the consent banner. The screenshots are in the session scratchpad and are not committed.

**Two places to review.**
1. A **Summary page**, with tabs *Summary · Changes (count) · Checks & reports · Threads · History*. It shows:
   - change totals as added, changed and removed, in a ring chart
   - a "review readiness" verdict (for example "Not ready, 1 of 4 requirements met, 3 blocking")
   - required checks (ERC, DRC, parity, BOM completeness), each with "New: n" and "Total: n errors, n warnings"
   - additional checks, reports and artifacts
   - a changed-files list with a preview of the head render
2. An **Inspect workspace** (`/inspect?view=canvas&fileId=…`). This is the screen this plan copies.

**Inspect workspace regions** (screen 1600 px wide):
- **Top bar.** Back, the review number, the title "Compare a4db…7de6", a status tag, then a *View mode* segmented control: **Side by side · Revision · Overlay · Wipe · Semantic**. At the right is a **Canvas | List** switch and buttons to collapse each side panel.
- **Left panel, about 225 px:**
  - A **Files** list with a "Changed only" toggle. Each file shows its icon, its name, and three count chips: `+21` green, `−3` red, `↻117` amber. KiHub lists every `.kicad_sch` file as its own entry, a flat list with no hierarchy tree.
  - Below the files, tabs **Layers · Objects · Details** for boards, or **Details** only for schematics.
  - The **Layers** tab has a "Presets: All Layers" dropdown, a "Group" toggle, and layers grouped under the headings *Top, Bottom, Board, User*. Each layer has an eye toggle, a colour swatch and its name, plus an "Active: 27/27" count.
  - The **Objects** tab has opacity sliders for tracks, vias, pads, holes, zones, grid and page, plus Front/Back footprint toggles.
  - The **Details** tab shows the selected object's properties ("No object selected — double-click an object on the canvas or a change row").
- **Centre canvas.** For both schematics and boards the background is a light paper colour, even though the interface is dark. A small corner label names what is shown: "Head revision", "Base" / "Head", "Base ■ Head ■" in overlay, or "Semantic Diff" with a legend of Added, Removed and Changed. A floating zoom bar at the bottom holds −, 345 %, +, fit, pan, a comment tool, a HEAD/BASE toggle and a brightness control. The drawing is a `<canvas>` (raster), not SVG.
- **Right panel, about 300 px.** Tabs **Changes · Inventory · Threads**. Below them:
  - a search box ("Search ref/value/net/layer…")
  - toggle chips *Added 24 · Removed 17 · Changed 163*, which filter when clicked
  - an "All sections" dropdown
  - section headings with counts, for example "FOOTPRINTS 10" or "COMPONENTS 91"

  Each change is a **card**:
  - the reference in bold, a layer badge (`B.Cu`), and a status badge with a glyph: `＋ Added`, `− Removed`, `→ Moved`, `≡ Changed`
  - then property rows, for example `Value 1uF`, `Footprint dX −0.6 · Rotation 180 → 90`, `Value text 10µ X7R 1210 → 10µ X7R 1210`
  - and a "+1 details" expander

**Comparison modes:**
- **Side by side**: Base and Head panes that move together.
- **Revision**: one revision at a time, with a HEAD/BASE toggle.
- **Overlay**: base tinted red and head tinted green, over the paper background.
- **Wipe**: a vertical divider, Base on the left and Head on the right.
- **Semantic**: the board darkened, with changed objects drawn in solid green, red or amber.

**Change row ↔ drawing.** Clicking a card zooms to the object (345 % to 2000 %). The head pane fills the object in blue, the base pane outlines the same spot, the card gets an orange border, and the URL gains `&changeId=board-footprint:<hash>`. I did not try selecting by clicking the canvas, because the Details tab said that needs a double-click.

**Checks** live on their own page (`/checks/erc`):
- A left list of checks, each with New / Total counts.
- A *Scope: Changes | Current* switch.
- Filter chips: *All · Errors · Warnings · New · Resolved*.
- A file filter.
- A table with the columns Severity, State (a `NEW` badge), Rule, Message, Base, Head, and Action (*View* jumps to the location).

**List view.** A table per section ("Components 91 changes — reference, value, connectivity and field changes"). Its columns are Change, Reference, Value, Key delta, Details and Visual, with filters for Status, Section and search.

**Colours.**
- **Change colours:** added green, removed red, changed amber or orange. Every badge also carries a glyph and a word.
- **Selection and accent:** orange.
- **Overlay:** red base, green head.

**Could not see or not verified:**
- The Supademo walkthrough. I did not open it.
- The Threads, Inventory and History tabs.
- KiHub's light theme. Only dark was seen, plus the canvas brightness toggle.
- Keyboard shortcuts. None were advertised in the page, and I found no `kbd` or `aria-keyshortcuts` attributes.
- Selecting by double-clicking on the canvas.
- How a hierarchical sheet tree would look. Every demo uses separate files.
- The *Revision* toggle.
- Scrolling deep into the change list.

**Differences from KiHub, with reasons:**
- **The navigator shows the sheet hierarchy** as an indented tree with counts per sheet. Your brief asks for "hierarchical schematics … with changed sheets marked", and we already know the UUID paths.
- **Checks are a tab in the right panel, not a separate page,** so clicking a violation moves the drawing without leaving the screen.
- **The canvas background follows KiCad, not the theme:** paper `#F5F4EF` for schematics and KiCad's `#001023` for boards, in both themes. KiCad's own layer colours are designed for these backgrounds. The theme only changes the interface around the drawing.
- **"Blend"** (opacity slider) is our name; KiHub has no equivalent. **"Semantic"** is our changed-regions-only mode, because KiHub's Semantic mode is the same idea: dim everything, mark what changed.
- **No Revision, Inventory, Threads or Objects-opacity tabs.** Not requested, YAGNI.

### A3. Drawing display: measured, decided

Measured on 2026-10-07 in headless Chrome 1600×1000 with the software renderer, on KiCad's `vme-wren` demo board. That board has 15 copper, silk and edge layers, 18 MB of SVG (3.6 MB gzipped) and 76k elements per copy. Two copies were on screen, 152k DOM elements in total. The test animated 120 frames of pan plus zoom:

| Approach | median frame | p95 | max |
|---|---|---|---|
| inline SVG, plain CSS transform | 16.7 ms | 64.7 ms | 136 ms |
| SVG as `<img>` (re-rasterised per zoom step) | 116.6 ms | 166.9 ms | 211 ms |
| **inline SVG + `will-change: transform` during the gesture** | **16.7 ms** | **17.6 ms** | **17.9 ms** |

**Decision: inline SVG with `will-change: transform` set only while a pan or zoom gesture runs.** It is removed 150 ms after the last input, so the browser re-rasterises sharply in about 5 ms. No library and no canvas renderer are needed. The cost is a short blur while zooming. Not verified: a real GPU, where it should only be faster, and Safari and Firefox.

### A4. Linking a change row to a shape: by coordinates

KiCad 10 SVGs carry no object ids: no `id=`, no UUIDs, only styled `<g>` groups (checked earlier in this project, and by sol). So the page locates objects by coordinates, and **the workflow does not need to emit identifiers into the SVGs.**
- Every change row already has `pos` and a `box` in drawing millimetres: pad extents for footprints, start/end for tracks, the outline for zones, a ±3 mm box for symbols and labels.
- Clicking the drawing converts the pointer position to millimetres and selects the smallest box containing that point, within 0.5 mm.
- Known limit: in dense areas the smallest box wins, which may not be the shape the reviewer aimed at. A second click cycles to the next box that contains the point.

### A6. Decision for the user: getting from a pull request to this screen

**Constraints:** private repositories, GitHub Free, no server, no published designs.

| # | Option | Steps for a reviewer | Private? | Notes |
|---|---|---|---|---|
| 1 | Today: zipped artifact | click link → download zip → unzip → open | yes | clumsy |
| 2 | **Unzipped artifact** (`upload-artifact@v7` `archive: false`) | click link → open the downloaded `kicad-review.html` | yes, GitHub login required | **Not yet tested:** whether GitHub serves it as a download (likely) or opens it in the tab |
| 3 | `gh` one-liner in the comment: `gh run download <id> -R <repo> -n kicad-review.html && open kicad-review.html` | paste one command | yes | needs `gh` installed and logged in; nothing to build except comment text |
| 4 | HTML on the `kicad-review-assets` branch, opened via `github.com/<repo>/raw/…` | — | yes | **does not work**: GitHub serves raw HTML as `text/plain` and does not render it (known behaviour; not tested here) |
| 5 | GitHub Pages | one click | **no** | Pages from a private repo needs Pro/Team, and the site is public except on Enterprise. Publishes the designs. Rejected |
| 6 | A public viewer page that fetches the private data in the reader's browser with their own GitHub token | one click, then a token prompt | yes | needs token handling, which amounts to sign-in, excluded by the brief; artifact downloads across origins are untested. Not now |

**Recommendation: options 2 and 3 together.** The comment links straight to the single HTML file, which is one click and one open instead of four steps. It also shows the `gh` command for people who live in a terminal. Together they need about 10 lines of change. The screenshots already in the comment answer most reviews without opening the report at all.

**Consequence for "paste an address into GitHub" (affects Task 9).** The page is opened from each reviewer's own downloads folder, so a full `file:///…` address is useless to a colleague. The page will instead copy a **position link**: the review link plus a fragment, for example `PR #2 · kicad-review #v=board&x=158.8&y=78.2&z=12&s=c12`. It also gets a **"Go to…" box** that accepts a pasted fragment or a whole pasted line and applies it. That is the honest equivalent without a server.

```python
def assign_ids(projects):
    """Give every change row and violation an id unique within this report, for selection and addresses."""
    n = 0
    for p in projects:
        for r in p["changes"]:
            n += 1
            r["id"] = f"c{n}"
    n = 0
    for p in projects:
        for c in p["checks"]:
            for v in c["violations"]:
                n += 1
                v["id"] = f"v{n}"


def review_links(env, det):
    """github.com links for the header. Empty strings outside GitHub Actions."""
    server, repo = env.get("GITHUB_SERVER_URL", ""), env.get("GITHUB_REPOSITORY", "")
    if not (server and repo):
        return {"review": "", "base": "", "head": "", "run": ""}
    base_url = f"{server}/{repo}"
    pr = env.get("PR_NUMBER", "")
    return {
        "review": f"{base_url}/pull/{pr}" if pr else (f"{base_url}/compare/{det['base']}...{det['head']}" if det["base"] else ""),
        "base": f"{base_url}/commit/{det['base']}" if det["base"] else "",
        "head": f"{base_url}/commit/{det['head']}",
        "run": f"{base_url}/actions/runs/{env['GITHUB_RUN_ID']}" if env.get("GITHUB_RUN_ID") else "",
    }
```

const cache = {};
async function svgText(id) {
  if (!id) return null;
  if (!(id in cache)) {
    const bin = Uint8Array.from(atob(D.blobs[id]), c => c.charCodeAt(0));
    cache[id] = await new Response(new Blob([bin]).stream().pipeThrough(new DecompressionStream("gzip"))).text();
  }
  return cache[id];
}
const DEFAULT_LAYERS = /^(F|B|In\d+)_Cu$|^(F|B)_Silkscreen$|^Edge_Cuts$/;
function layersOn() {
  const p = proj();
